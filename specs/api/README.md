# Fieldframe API documentation (OpenAPI)

This directory documents the Fieldframe Next.js backend API **as it is actually
implemented**. It is a documentation layer only: nothing under `apps/web` was
changed to produce it, and no endpoint, field, status code, or auth mechanism here
was invented ahead of the implementation.

## Files

```
specs/api/
  openapi.yaml               root document: info, tags, security, all paths, component refs
  schemas/
    common.yaml               ApiError envelope, Cuid, Timestamp
    authentication.yaml       session/user DTOs, login/signup/profile/password request bodies
    assets.yaml                Asset DTO, presigned/complete-upload, dataset asset list
    annotations.yaml          IMAGE annotation DTO + geometry union, AnnotationChangeSet,
                               and the VIDEO sub-domain (object tracks, keyframes, temporal labels)
    ai.yaml                    AI model listing, AI pre-annotation task create/read/cancel
    jobs.yaml                  Job read/cancel/retry/events, import commit, export (Job type EXPORT_DATASET)
    dataset.yaml                Dataset CRUD
    labels.yaml                Label CRUD
    import-repository.yaml    repository-backed Dataset creation, source connections,
                               Gitea repo browsing, local-folder import flow
    media.yaml                  VIDEO/AUDIO media-processing scheduling/readiness, IMAGE dimensions backfill
  dist/                        generated by `pnpm docs:build` -- gitignored, never hand-edited
    openapi.bundle.yaml         single self-contained bundle (all $refs resolved)
    index.html, swagger-ui-*    standalone offline Swagger UI page
```

`openapi.yaml` is OpenAPI 3.1 with relative `$ref`s into `schemas/*.yaml`. Any
standard OpenAPI 3.1 tool that resolves relative refs (Redocly CLI, Stoplight
Studio, the VS Code OpenAPI extension, `swagger-cli`) can load `openapi.yaml`
directly. A tool that only accepts a single fetched URL (e.g. pasting a raw
GitHub link into an online editor, or a plain static-HTML Swagger UI page)
needs everything bundled into one file first -- see "Bundling and a standalone
Swagger UI" below.

## Bundling and a standalone Swagger UI

```sh
pnpm docs:build
```

Runs three steps in order and writes everything to `specs/api/dist/` (a
**generated, gitignored build directory** -- `openapi.yaml` and `schemas/*.yaml`
remain the only source of truth; nothing under `dist/` is ever hand-edited):

1. `pnpm docs:validate-openapi` -- see "Validating" below; the build stops here
   if the source spec doesn't match the route inventory.
2. `pnpm docs:bundle-openapi` (`scripts/bundle-openapi.py`) -- merges
   `openapi.yaml` + every `schemas/*.yaml` into one self-contained
   `specs/api/dist/openapi.bundle.yaml`, mechanically rewriting every relative
   `$ref` into a single global `#/components/schemas/<Name>` form. Pure
   rewriting only -- it does not add, remove, or alter any documented path,
   schema, or field. Uses system `python3` + `PyYAML`, consistent with the
   validator, so no Node bundler package (`@redocly/cli`, `swagger-cli`, ...)
   was added.
3. `pnpm docs:swagger-ui` (`scripts/generate-swagger-ui.mjs`) -- copies the
   static assets from `swagger-ui-dist` and writes `specs/api/dist/index.html`,
   a fully offline Swagger UI page that loads `./openapi.bundle.yaml`.

**This is a standalone documentation artifact, not part of the running
application.** `scripts/generate-swagger-ui.mjs` never touches anything under
`apps/web` -- there is no `/api-docs` Next.js route, and `swagger-ui-dist` is a
devDependency of the **repo root only** (`package.json`, not
`apps/web/package.json`), so it cannot end up in the production Next.js
build/bundle. To view the docs: open `specs/api/dist/index.html` directly in a
browser, or serve `specs/api/dist/` with any static file server
(`npx serve specs/api/dist`, GitHub Pages, an internal docs bucket, etc.) and
share that link with colleagues -- separately from deploying the app itself.

`@scarf/scarf` (an anonymous install-telemetry pinger pulled in transitively by
`swagger-ui-dist`) has its postinstall script explicitly disallowed in
`pnpm-workspace.yaml`'s `allowBuilds` -- it is not required for the static
JS/CSS assets this script actually uses.

### Review environment testing

**`http://10.0.0.123:3001/docs`** serves this same standalone Swagger UI
page, same-origin with the Review app and its API (`http://10.0.0.123:3001/`,
`http://10.0.0.123:3001/api/...`). "Try it out" -> login -> authenticated
calls all work with zero CORS configuration, because there is no cross-origin
request anymore -- confirmed end-to-end (login sets `fieldframe_session`,
then an authenticated `GET /api/auth/me` succeeds using it, all through
`:3001`).

This is a **Review-only nginx reverse proxy** (`docker/review-proxy.conf`, a
new `proxy` service in `docker-compose.review.yaml`), not an application
change:

- `proxy` is the only container publishing a host port (`3001`) in the Review
  stack now. It serves `/docs`, `/docs/`, and `/docs/*` directly from a
  **read-only bind mount of the host's `specs/api/dist/`** (no image rebuild
  to pick up a new `pnpm docs:build` -- nginx reads files fresh per request),
  and reverse-proxies everything else, unchanged, to the `web` service
  (`web:3000`) over the compose network -- `web` no longer publishes a host
  port directly.
- Dev (`docker-compose.yaml`, and the bare `pnpm dev` most commonly used
  instead of it) is untouched: this proxy is defined only in
  `docker-compose.review.yaml`.
- No Next.js route, no `swagger-ui-react`, no app-runtime dependency: nginx
  never touches `apps/web`. `swagger-ui-dist` remains a root-only
  devDependency used solely to generate the static page consumed here.
- Bare `/docs` (no trailing slash) 301-redirects to `/docs/` rather than
  serving `index.html` directly at that exact path: the generated page's
  asset references are relative (`./swagger-ui.css`, `./openapi.bundle.yaml`,
  ...), and a browser resolves those against `/docs` (no slash) as `/x`, not
  `/docs/x` -- confirmed by testing both against the running proxy. This is
  the same directory-URL normalization virtually every static host applies;
  `curl -I` on the bare path will show `301`, and `curl -IL` (or a browser)
  ends at `200` on `/docs/`.
- Prerequisite: `specs/api/dist/` must exist on the host (`pnpm docs:build`)
  before `docker compose -f docker-compose.review.yaml up`/`restart proxy` --
  the bind mount doesn't generate it. Re-running `pnpm docs:build` after a
  spec change is picked up immediately, no restart needed.

The `python3 -m http.server 8080` standalone-preview workflow (see the
`servers:` entry for `http://10.0.0.123:3001` in `openapi.yaml`) still works
unchanged for a quick local preview without the Review stack running --
but for anything a colleague needs to actually exercise against the Review
API, `/docs` above is the one that needs no CORS workaround.

## Validating

```sh
pnpm docs:validate-openapi
# or: python3 scripts/validate-openapi.py
```

The script (`scripts/validate-openapi.py`) checks YAML syntax, that
`openapi.yaml` is version 3.1.x, that all nine required tags exist, that every
`$ref` into a schema file resolves, that every documented path+method
corresponds to a real `apps/web/src/app/api/**/route.ts` handler (and reports,
without failing, actual routes not documented -- today only `GET /api/health`),
and specifically asserts that `/api/assets/{assetId}/annotations` is documented
with exactly `GET`+`PUT` and that `/api/annotations` is not documented.

It uses the system `python3` + `PyYAML` rather than adding a Node/npm
OpenAPI-parser dependency, per AGENTS.md's "do not add npm packages without
explicit permission." If the team would rather have a Node-native validator
(e.g. `@apidevtools/swagger-parser` or `@redocly/cli`) as a devDependency, that
is a one-line ask away but was not added here without that sign-off.

## Scope

All 50 non-health route files under `apps/web/src/app/api` are documented,
grouped into nine tags: **Authentication**, **Assets**, **Annotations**, **AI**,
**Jobs**, **Dataset**, **Labels**, **Import / Repository**, **Media**.

`GET /api/health` is the one deliberate exclusion: it is an unauthenticated
liveness probe with no request/response contract worth documenting as a product
API, and none of the nine tags fit it. If a System/Health tag is wanted later,
say so and it can be added as a tenth tag without touching anything else here.

### Tag placement notes (routes that don't map 1:1 to a URL prefix)

- **Annotations** covers both the original IMAGE batch endpoint
  (`GET`/`PUT /api/assets/{assetId}/annotations`) and the entire VIDEO annotation
  sub-domain -- `video-annotations`, `video-object-tracks`, `video-keyframes`,
  `temporal-labels` -- because all of it persists as `Annotation`/
  `VideoObjectTrack` rows, not Asset or Job metadata.
- **Media** covers only VIDEO/AUDIO media-processing scheduling/readiness and the
  IMAGE `dimensions` backfill route. It does not cover VIDEO annotation reads/writes
  (see above) even though both are asset-scoped and video-adjacent.
- **Jobs** covers `POST /api/export` and `GET /api/export/{jobId}` -- an export is
  a `Job` of type `EXPORT_DATASET`, read/written through the same safe Job
  projection as every other Jobs route, not a separate resource.
- **Import / Repository** includes two routes that always return `410 Gone`
  (`POST /api/gitea/import`, `POST /api/source-import-jobs`). They are real,
  reachable route handlers, so they are documented (marked `deprecated: true`)
  rather than omitted, with their responses pointing at the current successor
  endpoint (`POST /api/datasets/from-repository`).

## OpenAPI 3.1 style conventions (Swagger Editor compatibility)

This spec targets OpenAPI 3.1 (full JSON Schema 2020-12 for Schema Objects), not
3.0. Two 3.0-era habits are avoided throughout on purpose, because Swagger
Editor and other 3.1-aware tools flag them:

- **No `nullable: true`.** It has no meaning in 3.1 -- JSON Schema expresses
  nullability through the `type` keyword itself. A plain typed field uses a type
  array: `type: [string, "null"]`. A field whose type comes from a `$ref` (which
  can't take a sibling `type:` without contradicting the referenced schema) uses
  `oneOf: [{ $ref: ... }, { type: "null" }]` instead. Every occurrence in this
  spec was converted this way -- see `git log` / the diff that introduced this
  section for the full sweep across `openapi.yaml` and every `schemas/*.yaml`.
  Nullability itself was never removed: every field that can genuinely be
  `null` in the real API response still documents that.
- **No singular `example:` inside a Schema Object.** Two different constructs
  both used to be called `example` pre-3.1 and are easy to conflate:
  - A **Media Type Object** example (`content.application/json.example`, used
    on request/response bodies in `openapi.yaml`) becomes the Example Object map
    form: `examples: { default: { value: ... } }`.
  - A **JSON Schema** example (an `example:` sibling inside a `properties.*`
    schema, e.g. `Cuid`'s sample id in `schemas/common.yaml`) becomes the
    JSON-Schema-native `examples:` **array**: `examples: [value]`. This is a
    different shape from the Media Type Object form above -- do not confuse the
    two when adding new examples.

**The three `DELETE` `requestBody`s are intentional and were kept.** Swagger
Editor separately warns that `requestBody` "does not have well-defined
semantics" for GET/HEAD/DELETE -- that is general REST-style guidance the
OpenAPI spec itself states as advisory, not a hard validation rule, and it does
not override what this API actually does. `DELETE /api/video-object-tracks/{trackId}`,
`DELETE /api/video-keyframes/{annotationId}`, and
`DELETE /api/temporal-labels/{annotationId}` all read a required JSON body
(`expectedTrackRevision` / `expectedRevision`) and reject the request with `409`
if it's missing or stale -- verified directly against
`apps/web/src/lib/annotations/video-track-service.ts`,
`video-keyframe-service.ts`, and `video-temporal-label-service.ts`. Moving that
revision into a query parameter would be an API redesign, which is explicitly
out of scope for this documentation layer -- the body stays, each operation's
`requestBody.description` explains why, and Swagger Editor's advisory warning
is expected to remain visible for these three operations. That's the intended
outcome: accurate documentation over a quieter linter.

## Implementation notes worth knowing before extending this document

- **Not a redesign.** `GET`/`PUT /api/assets/{assetId}/annotations` is the real,
  Asset-scoped route. There is no `/api/annotations`.
- **`GITEA_NOT_FOUND` is a generic "hidden not found" code**, not
  Gitea-specific. It's returned by `hiddenNotFound()`
  (`apps/web/src/lib/authorization-response.ts`) and reused for dataset-not-found
  and asset-not-found responses across many domains (Assets, Dataset, Labels,
  Media's image-dimensions route), apparently a holdover from when Gitea import
  was the only import path. This is documented as-is (implementation wins)
  rather than renamed, per the task's instructions -- but it's a naming smell
  worth a follow-up rename ticket outside this task's scope.
- **`AnnotationType` (read) is broader than the write-accepted type set.**
  `GET` can return any Prisma `AnnotationType` (including types like
  `SEGMENTATION_MASK` or `IMAGE_CLASSIFICATION` produced by other paths, e.g. the
  AI prediction pipeline in `apps/worker`), while `PUT .../annotations` only
  accepts `BOUNDING_BOX | POLYGON | CIRCLE | POINT | POLYLINE`
  (`imageAnnotationGeometrySchema`). Documented as two separate schemas
  (`AnnotationType` vs `WritableAnnotationType`) rather than treated as a
  mismatch to resolve -- it is consistent, intentional asymmetry between read and
  write. The VIDEO sub-domain is narrower still: keyframes are always
  `BOUNDING_BOX`, and temporal labels are always `EVENT | SCENE | SHOT_BOUNDARY`.
- **IDs are mostly CUIDs**, not UUIDs. `datasetId` and `jobId` path/body params
  accept either (`z.union([cuid(), uuid()])`) because local-folder imports
  generate UUIDs before persistence. `assetId`/`trackId`/`annotationId` path
  params are not format-validated by their routes at all (used as raw strings in
  Prisma queries) -- documented as `type: string`, not constrained to a CUID
  pattern, to avoid overclaiming validation the server doesn't perform.
- **Two routes in the same domain use different auth-context checks.**
  `POST /api/auth/refresh`, `POST /api/auth/password`, and
  `PATCH /api/auth/profile` add a same-origin (Origin header) check on top of the
  session cookie; the rest of the API relies on the session cookie alone. This
  is documented in each operation's description rather than as a separate
  security scheme, since it is not a distinct credential -- it is an additional
  server-side check on the same cookie-authenticated request.
- **No mismatches found** between any route's Zod validation schema and its
  service-layer behavior that would require a blocker/TODO callout -- each
  domain's schema and service code were read together and are consistent.

## Not done (explicitly out of scope)

- No Swagger UI **route** exists in the Next.js app (`/api-docs` or
  otherwise) -- the standalone page in `specs/api/dist/` is the only Swagger UI,
  and it is a build artifact, never served by `apps/web`.
- No changes were made to any route, schema, validation, or service file.
- `GET /api/health` remains undocumented (see "Scope" above).
