# Quickstart: Validating the Asset Browser & Dataset Management Workspace

Validation scenarios that prove the feature works end-to-end, mapped to the spec's user stories and success criteria. Not a task list or implementation guide — see [tasks.md](./tasks.md) (generated by `/speckit-tasks`) for that.

## Prerequisites

- Local stack running per the project's existing Docker Compose setup (`postgres`, `redis`, `minio`, `web`, `worker`).
- `pnpm db:migrate` applied (includes this feature's `AssetLabel` model, `Asset.assignedToId`, and the two new `JobType`/`JobStage` values).
- A seeded Dataset with: ≥25 Assets spanning all four modalities, at least one Asset per `AssetStatus` value used in review-status testing (`NEEDS_REVIEW`, `REVIEWED`, `REJECTED`), at least one Label, at least one Annotation referencing that Label, and one Asset with a deliberately missing `storageKey` (for the health check scenario).
- A second, unrelated Dataset the test user does **not** have access to (for authorization-boundary scenarios).

## Scenario 1 — Discover and inspect (User Story 1 / SC-001)

1. Open the seeded dataset's workspace, select any asset to land in the Properties Panel's Assets tab.
2. Enter a search term matching a subset of filenames → confirm only matches appear and the Previous/Next controls reflect the smaller result count.
3. Add a modality filter, then a status filter, then a label filter, all at once → confirm the result set is the intersection of all three, not the union.
4. Change sort to "Updated date, descending" → confirm the same result *set* reorders without any item appearing/disappearing.
5. Page forward with Previous/Next while the above filters are active → confirm results stay consistent with the active query across pages.
6. Click into an IMAGE asset, then a VIDEO asset, then an AUDIO asset, then a TEXT asset from the filtered list → confirm each shows real modality-specific details (Audio/Text now show populated fields, not just a filename).

**Pass condition**: All of the above with the network tab showing only bounded page-sized responses — never a request whose payload size scales with total dataset asset count.

## Scenario 2 — Select and organize (User Story 2 / SC-002, SC-003, SC-009)

1. With a filter active matching more than 10 assets, click "Select all filtered" → confirm the UI shows "N assets selected" where N is the true filtered count, and confirm (via network inspection) no request fetched every matching asset's full record.
2. With that selection active, run "Add Label," choosing an existing label → confirm the result summary (`processed/succeeded/failed/skipped`), then re-run the identical action → confirm the repeat reports the assets as `skipped`, not `failed`, and no duplicate `AssetLabel` rows exist (spot-check one asset).
3. Run "Add Label" again, this time creating a brand-new label with a name and color inline → confirm it now also appears in the standalone Labels tab, following the same naming/uniqueness rules (attempt a duplicate name → rejected/reused, not duplicated).
4. Select assets known to have an Annotation referencing a given Label, run "Remove Label" on that label → confirm the annotation-reference warning appears before removal, confirm proceeding removes the Asset-Label attachment while the underlying Annotation is unchanged (verify via the asset's existing Annotation view).
5. Run "Change Status" on a selection → confirm only `Asset.status` changed; spot-check that `Annotation.status`, `Job.status`, and any `AiTask.status` for those assets are untouched.
6. With an explicit (individually-clicked) selection active, change the active filter so some selected assets drop out of view → confirm the selected count stays accurate and the UI distinguishes visible-and-selected from hidden-but-selected.
7. With only sort order changed (no filter/search change) → confirm the selection (either mode) is completely unaffected.
8. Open "Assign," pick a dataset member → confirm the assignment entry point works and only applies to the current selection.

**Pass condition**: every step's result summary is visible and accurate; no step silently reports full success while an item was actually skipped/failed.

## Scenario 3 — Bulk delete safely (User Story 3 / SC-004)

1. Select a small batch (under the sync threshold) of assets, delete → confirm confirmation prompt appears before anything is removed, confirm deleted assets vanish from the list immediately.
2. Verify (directly, e.g. via a MinIO listing or the existing orphan-scanner dry run) that storage objects belonging to assets **outside** this deletion remain present, and that the deleted assets' objects are eventually cleaned up (may be asynchronous — poll or check the cleanup job).
3. Select a batch above the sync threshold, delete → confirm the UI states this will run in the background, confirm a Job is created and its terminal state/result is checkable.
4. Attempt to delete via a manipulated request referencing an asset ID from the unrelated second dataset → confirm it's rejected/skipped, never deleted.
5. Retry the same background delete Job (or resend the identical bulk request) → confirm already-deleted assets don't error and nothing duplicates.

**Pass condition**: no asset outside the selected/authorized set is ever affected; deletion never blocks on MinIO availability.

## Scenario 4 — Export Selected (User Story 4 / SC-005)

1. Select a subset of assets across multiple modalities, run "Export Selected" from the Workspace Toolbox.
2. Once complete, download and inspect the result → confirm it contains selected assets' metadata, labels, and annotation records, and confirm zero binary bytes (no image/video/audio content) are present.
3. Run the existing full Dataset Export separately → confirm its output/behavior is unaffected by having just run Export Selected.
4. Use "Select all filtered" against a large matching set, export → confirm it becomes a background Job rather than a large synchronous response.

**Pass condition**: Export Selected and Dataset Export produce independent artifacts with independent idempotency keys; neither disturbs the other.

## Scenario 5 — Dataset overview and health (User Story 5 / SC-006)

1. Open the seeded dataset's overview → confirm total asset count, per-modality counts, annotation count, progress, and created/updated timestamps match the known fixture state.
2. Confirm the deliberately-broken asset (missing `storageKey`) is surfaced under Dataset Health.
3. Confirm nothing under Dataset Health resembles an annotation-quality/agreement/accuracy metric.
4. Edit the dataset description (if the current user's role permits it) → confirm it saves and reflects immediately; confirm a role without edit permission cannot.

**Pass condition**: every displayed number is independently verifiable against the fixture data without querying the database directly.

## Scenario 6 — Canvas/annotation regression guard (SC-007, FR-039)

1. Run the full existing image and video annotation test suites unmodified → confirm 100% pass, no test needed updating because of this feature.
2. Manually draw, edit, and delete a bounding box on an IMAGE asset; manually create/edit a keyframe on a VIDEO asset → confirm behavior is pixel-for-pixel identical to pre-feature behavior (pan/zoom, autosave timing, optimistic-locking conflict message on a simulated stale write).

**Pass condition**: zero observable difference in Canvas behavior.
