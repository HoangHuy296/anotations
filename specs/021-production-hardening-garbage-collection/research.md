# Phase 0 Research: Production Hardening and Garbage Collection

Each section resolves one open technical decision needed before Phase 1 design. Every decision is grounded in what the repository audit (below) found already exists, per AGENTS.md's "do not duplicate existing mechanisms; reuse existing patterns where possible."

## Repository & Architecture Audit Summary

This is section 1 of the original request, completed as the first research task since every later decision depends on it.

**Job infrastructure** (`prisma/schema.prisma` `model Job`): `status` (`QUEUED`/`RUNNING`/`RETRYING`/`COMPLETED`/`FAILED`/`CANCELING`/`CANCELED`, no `DEAD` value), `lockedBy`/`lockToken`/`lockedAt`/`lockedUntil`/`heartbeatAt` (lease fields), `attempts`/`maxAttempts` (default 3), `runAfter`, `idempotencyKey`, `retryOfJobId` (self-relation, successor lineage), `errorCode`/`errorDetails`. `JobEvent`: append-only, `level`/`stage`/`message`/`data`/`createdAt`, indexed on `(jobId, createdAt)`.

- **Job creation**: e.g. `apps/web/src/lib/imports/prepare-local-folder-import.ts` — creates the `Job` row inside the same transaction as its domain record, `status: QUEUED`.
- **Job claiming**: `apps/worker/src/jobs/job.repository.ts#claimJob` — one parameterized `UPDATE ... WHERE status IN ('QUEUED','RETRYING') AND (lockedUntil IS NULL OR lockedUntil < NOW()) RETURNING *`. This is the repository's one AGENTS.md-approved raw-SQL exception (Phase 008).
- **Lock renewal**: `apps/worker/src/queue/job-lock.ts#renewOrReclaimLock`/`renewLock`/`releaseLock` — same atomic-conditional-`UPDATE` idiom, currently used only by the AI-poll scanner re-entering an already-`RUNNING` Job.
- **Worker startup / BullMQ config**: `apps/worker/src/readiness.ts` → `createFoundationWorker` (`apps/worker/src/queue/bullmq-worker.ts`) constructs one BullMQ `Worker` with only `{ connection, prefix }` — **no `lockDuration`, `stalledInterval`, or `maxStalledCount` configured** (confirms this is a real gap, not already handled).
- **Redis connection handling**: `apps/worker/src/queue/bullmq-worker.ts` opens one `ioredis` connection per foundation worker (`maxRetriesPerRequest: null`, ioredis's own auto-reconnect applies); no `apps/web`-side Redis client exists at all today.
- **Existing recovery behavior**: `apps/worker/src/queue/recovery-scanner.ts#runPendingJobRecovery` is **fully implemented and unit-tested** (`apps/worker/tests/queue/recovery-eligibility.test.ts`) but **never invoked anywhere in the running worker** — not called from `readiness.ts`, not scheduled. It only re-delivers `Job`s stuck at `status: QUEUED, enqueuedAt: null` (i.e., the durable record exists but the BullMQ enqueue never happened or was never observed) — this is precisely the Redis-outage-recovery mechanism User Story 2 needs; it just needs to be wired up.
- **Existing cancellation behavior**: `cancelRequestedAt`/`canceledAt`/`canceledById` fields exist; `recovery-scanner.ts` already skips a candidate whose `cancelRequestedAt` is set.
- **No general stale-`RUNNING` recovery exists**: nothing scans for `Job`s where `status = 'RUNNING' AND lockedUntil < NOW()` for job types other than the AI-poll path. If a worker crashes mid-processing of e.g. an export or import job, that job's lease silently expires and nothing currently reclaims or fails it. **This is the core new gap User Story 1 fills.**

**Storage infrastructure**:
- **MinIO client**: `apps/worker/src/providers/minio.ts`, `apps/web` via `minio` SDK directly in route/lib code.
- **Object key generation / asset→object relationship**: `Asset.storageProvider`/`storageBucket`/`storageKey` (unique together); `Asset.checksum`; presigned upload flow in `apps/web/src/lib/asset-upload.ts` + `apps/web/src/lib/client/direct-upload.ts` — a browser uploads directly to its **final** object key via a presigned POST, then calls a publish endpoint that creates the `Asset` row referencing that same key. There is no separate "temp key" renamed to a "final key" on commit.
- **Existing cleanup mechanism (the pattern to generalize)**: `apps/web/src/lib/asset-upload.ts#cleanupUnpublishedObject` (best-effort, synchronous, called only when publish itself fails) and `apps/web/src/lib/imports/import-cleanup.ts#cleanupPreparedImportOrphans` (lists a `prepared-imports/{datasetId}/` prefix, deletes any key with no matching non-deleted `Asset` row). The latter is exactly the "list objects, check DB reference, delete if none" shape the orphan scanner/asset-cleanup/dataset-cleanup/temp-upload-cleanup all need — just not yet prefix-generalized, grace-period-aware, batched, dry-run-capable, or scheduled.
- **Lifecycle metadata**: none configured on the MinIO bucket today (no `BucketLifecycleConfiguration` call found).

## Decisions

### 1. Stale-`RUNNING` job recovery & dead-letter representation

- **Decision**: Add one new worker module, `stale-job-detector.ts`, using the same atomic-conditional-`UPDATE` idiom as `job.repository.ts#claimJob` / `job-lock.ts#renewOrReclaimLock`: `UPDATE "Job" SET ... WHERE status = 'RUNNING' AND lockedUntil < NOW() RETURNING *`. For each reclaimed row, branch in application code (not SQL) on `attempts < maxAttempts`: if under budget, increment `attempts`, clear lock fields, set `status = 'RETRYING'` (existing status, re-enqueued through the existing recovery-scanner delivery path) and write a `JobEvent`; if at/over budget, set `status = 'FAILED'`, `errorCode = 'RECOVERY_EXHAUSTED'` (or the detector's own reason), `finishedAt = NOW()`, and write a terminal `JobEvent`. No new `JobStatus` enum value, no new table.
- **Rationale**: Reuses 100% of the existing lease/lock/attempt fields and the exact locking idiom AGENTS.md's "do not invent a second locking mechanism" and the spec's "use existing lock/lease fields if available" both require. "Dead-letter" is fully derivable as `status = 'FAILED' AND attempts >= maxAttempts` (plus the recorded `errorCode`), so it needs no schema change and stays observable through the existing Job query surface — satisfying FR-010/FR-011 without a parallel dead-letter store.
- **Alternatives considered**: A new `JobStatus.DEAD` enum value — rejected, explicitly forbidden by "do not redesign the Job state machine without necessity" and unnecessary since the condition is derivable. A separate `DeadLetterJob` table — rejected, explicitly forbidden by AGENTS.md's non-negotiable data rules.

### 2. Redis/queue-outage recovery

- **Decision**: Wire the already-implemented, already-tested `recovery-scanner.ts#runPendingJobRecovery` into `readiness.ts`'s existing `setInterval` scheduling pattern (same shape as `failExpiredPreparedImports`'s 60s loop). No changes to its logic are needed for FR-016–FR-018; only its `redeliverExistingJob` callback needs a concrete implementation that calls the same enqueue path job creation already uses.
- **Deeper finding**: `apps/web/src/lib/queue/enqueue-job.ts#enqueueExistingJob` — the single call path every Job-creating route already goes through (`createAndEnqueueFoundationJob`, `createAndEnqueueSourceImportJob`, `createAndEnqueueNewDatasetSourceImportJob` all call it) — **already implements FR-016/FR-017 exactly**: its `try/catch` around `queue.add()` never stamps `queueName`/`queueJobId`/`enqueuedAt` on failure, writes a `QUEUE_DELIVERY_PENDING` JobEvent with `reason: "QUEUE_UNAVAILABLE"`, and returns `{ ok: true, status: 202, deliveryPending: true }` — an honest "accepted but not yet queued" signal, never a false "queued" success. So FR-016/FR-017 are **already correct today**; the actual gap is purely that nothing ever re-drives a `202 deliveryPending` Job back to delivery — which is exactly `recovery-scanner.ts`'s job, once scheduled.
- **Rationale**: The scanner was built and tested for exactly this scenario (`status: QUEUED, enqueuedAt: null`) during an earlier phase but never scheduled — this is a wiring gap, not a design gap, and the enqueue-failure honesty guarantee itself needs no new code at all, only test coverage and a structured-log call in its existing `catch` block.
- **Alternatives considered**: Building a new outage-recovery scanner — rejected as pure duplication of tested, working code. Auditing/rewriting every Job-creation route's enqueue call — rejected; all three already funnel through the one already-correct `enqueueExistingJob`.

### 3. BullMQ stalled-job handling

- **Decision**: Add `settings: { stalledInterval, maxStalledCount }` and a `lockDuration` to the one `Worker` constructor in `bullmq-worker.ts`. `lockDuration` bounds how long BullMQ waits before considering a delivery stalled; `maxStalledCount` bounds how many times BullMQ will redeliver before marking it failed on the BullMQ side. Because `claimJob`'s `WHERE status IN ('QUEUED','RETRYING')` guard already makes a redelivery to an already-`RUNNING` Job a safe no-op, BullMQ-level stall handling and the Postgres-level stale-`RUNNING` detector (decision 1) are complementary, not competing: BullMQ's redelivery gives fast in-process recovery when the same worker process is still alive but wedged; the Postgres detector is the durable backstop when the whole worker process is gone.
- **Rationale**: Directly satisfies FR-019–FR-021 using BullMQ's own built-in mechanism, per the spec's explicit instruction not to blindly map BullMQ state onto the Postgres record.
- **Alternatives considered**: Relying solely on the Postgres-side stale detector and leaving BullMQ stall handling off — rejected, spec explicitly asks BullMQ's own mechanism to be enabled/configured (section 5).

### 4. Import commit timeout

- **Decision**: No logic change to `import-timeout-scanner.ts#failExpiredPreparedImports` — it already correctly enforces `PreparedImport.deadlineAt` (currently `IMPORT_DEADLINE_MS = 30 * 60 * 1000`, 30 minutes, in `prepare-local-folder-import.ts`), already sets `PreparedImportStatus.EXPIRED`, already writes a `JobEvent`, and its query is already idempotent (re-matches nothing once `status` moves off `PREPARING`). Work here is: (a) confirm it is already scheduled — it is, via `readiness.ts`'s 60s `importTimeoutTimer` — so no wiring gap; (b) add the four test scenarios the spec asks for (commit before/after timeout, timeout cleanup, worker restart mid-commit) since none currently exist beyond the eligibility unit test; (c) verify commit-then-timeout-race behavior explicitly (a commit that lands in the same tick as expiry must not double-process).
- **Rationale**: This mechanism is materially complete already; the spec's ask is test coverage and confirmation, not new code, per "do not duplicate existing mechanisms."
- **Alternatives considered**: None — rebuilding this would directly violate "before implementing new infrastructure, reuse existing patterns."

### 5. MinIO orphan scanning, asset cleanup, dataset cleanup, and temp-upload cleanup — one shared primitive

- **Decision**: Extract `import-cleanup.ts#cleanupPreparedImportOrphans`'s shape ("list objects under a prefix" → "for each key, check `Asset` reference by `(storageProvider, storageBucket, storageKey)`" → "delete if unreferenced") into one new, reusable, prefix-and-grace-period-parameterized primitive in `apps/worker/src/queue/minio-orphan-scanner.ts`, with a `dryRun: boolean` flag and a grace period computed from each MinIO object's `LastModified`/`stat` time (no new Prisma table needed to track object age). Build the other three surfaces on top of it:
  - **MinIO orphan scanner** (FR-022–FR-025): the primitive run over the whole bucket (or a configured prefix set) on a schedule, `dryRun` by default configurable via env var.
  - **Deleted-asset cleanup** (FR-026/FR-027): on `Asset` soft/hard delete, enqueue a targeted single-key call into the same primitive (immediate best-effort + retryable), so the async cleanup job and the periodic full-bucket scan share one code path and one notion of "unreferenced."
  - **Deleted-dataset cleanup** (FR-028/FR-029): the primitive run scoped to the dataset's known asset storage keys, batched (bounded page size per batch, matching `cleanupPreparedImportOrphans`'s per-key isolation-of-failure pattern already in place).
  - **Temp-upload cleanup** (FR-030): the primitive run scoped to the `prepared-imports/{datasetId}/` and any other temp/staging prefix, using the *upload's own age* (there is no separate "active upload session" row for direct asset uploads — see below) as the grace-period input.
- **Rationale**: Directly satisfies AGENTS.md's "do not duplicate existing mechanisms" — four sections of the original request (13/14/15/16) collapse into one tested primitive plus three thin, purpose-specific callers, each independently schedulable/testable per FR-053 and independently satisfying the idempotency requirement (FR-031) because "unreferenced + past grace period ⇒ delete, else skip" is naturally idempotent no matter how many times or how concurrently it runs.
- **On "active upload session"**: the audit found direct (non-import) asset uploads have no durable "session" row — a browser uploads straight to the object's final key via a presigned POST, then calls a publish endpoint that creates the `Asset` row. An object with no `Asset` reference is therefore either (a) an upload that's still in flight / about to be published, or (b) truly abandoned — indistinguishable except by age. This is exactly what the grace period is for: it must be set comfortably longer than the presigned URL's expiry plus reasonable publish-call latency, so a genuinely in-flight upload is never mistaken for abandoned. `PreparedImport`-flow temp objects, by contrast, do have a durable session concept (`PreparedImport.status`/`deadlineAt`), so their cleanup can additionally skip anything under an *active* (non-`EXPIRED`, non-`COMMITTED`) `PreparedImport`.
- **Alternatives considered**: Four independent implementations (one per section 13–16) — rejected as direct duplication. A new "pending upload" tracking table — rejected as unnecessary schema growth when object age + the existing `PreparedImport` state already cover both upload paths conservatively (FR-032's "when uncertain, don't delete" is satisfied by a generous grace period, not by new bookkeeping).

### 6. Cross-worker coordination for scheduled maintenance passes

- **Decision**: For every pass whose destructive action is a single atomic conditional `UPDATE ... WHERE <still-eligible> RETURNING *` per candidate row (stale-job recovery, dead-letter transition, JobEvent retention delete, deleted-asset/dataset cleanup keyed by `Asset`/`Dataset` id) — no additional coordination lock is needed at all: two worker replicas racing on the same row simply both attempt the same conditional update and at most one succeeds, exactly like `claimJob` already relies on today. For the one pass that is *not* naturally row-atomic — the full-bucket MinIO orphan scan, which lists external MinIO state rather than claiming Postgres rows — wrap the scan in a PostgreSQL session-scoped advisory lock (`pg_try_advisory_lock`, released automatically on disconnect) keyed to a fixed constant for "orphan scan in progress," so only one worker replica runs the listing pass at a time; a replica that fails to acquire it simply skips that tick.
- **Rationale**: Matches "use existing lock/lease fields if available" and "do not invent a second locking mechanism" — a Postgres advisory lock is a built-in feature of the database this project already treats as authoritative, not a new external coordination system, and it is used for exactly one narrow, already-idempotent-if-it-does-double-run pass (the scan is safe to run twice per FR-031; the lock only avoids wasted duplicate MinIO listing work, not a correctness requirement).
- **Alternatives considered**: A new `SchedulerLease`/leader-election table — rejected, unnecessary given the row-atomic passes need no lock at all and the one listing pass is adequately served by a built-in Postgres primitive. A Redis-based distributed lock (e.g. Redlock) — rejected as heavier than needed and inconsistent with "Redis is transport only."

### 7. Rate limiting

- **Decision**: Redis-backed fixed-window counter (`INCR` + `EXPIRE` on a key like `ratelimit:{userId}:{routeCategory}:{windowStart}`), checked at the top of `POST /api/ai/tasks`, the import-initiation route(s), and the export-initiation route, before any `Job`/`PreparedImport` row is created. Requires adding `ioredis` (already pinned at `5.10.1` in `apps/worker`) to `apps/web`'s dependencies — **flagged in the plan's Constitution Check as needing explicit user sign-off**, since `apps/web` currently has zero Redis runtime dependency.
- **Rationale**: The spec explicitly prefers Redis-backed limiting "if Redis is already the platform-wide coordination layer" (it is, via BullMQ), and a fixed-window `INCR`/`EXPIRE` pair is the simplest correct primitive for "prevent one user from creating unlimited background jobs" without a new distributed-rate-limiter package.
- **Alternatives considered**: Postgres-backed counters (e.g. a row-per-user-per-window with `UPSERT ... SET count = count + 1`) — rejected as the non-preferred option per the spec's own wording, and it would add write load to the same transaction path as Job creation for a purely protective check; also considered but rejected: an npm rate-limiting middleware package — unnecessary given how small the primitive is, and AGENTS.md requires justifying any new package, so the smallest-footprint option (raw `ioredis` commands, already a vetted dependency in this monorepo) wins.

### 8. Pagination approach

- **Decision**: For `GET /api/datasets` and `GET /api/datasets/[datasetId]/labels`, add standard offset (`page`/`pageSize`) pagination matching the existing `GET /api/datasets/[datasetId]/assets` shape (`{ items, page, pageSize, total }` envelope already established there) — not a new envelope shape. `GET /api/jobs/[jobId]/events` already has cursor pagination and needs no change. Any additional unbounded endpoint found during the full audit (task 1 of implementation) gets the same offset shape unless it is itself an operational/high-volume table like `JobEvent`, which stays cursor-based like the existing endpoint.
- **Rationale**: FR-042 requires preserving the existing workspace asset pagination's response shape and, by extension, its conventions — reusing the same envelope everywhere keeps every paginated endpoint's contract predictable for existing and new callers alike.
- **Alternatives considered**: Cursor pagination everywhere — rejected as unnecessary complexity for small, non-operational collections like a dataset's own label list, and inconsistent with the already-established offset shape on the asset listing endpoint this feature must not change.

### 9. Structured logging

- **Decision**: No new logging library. Add one small internal helper (e.g. `apps/worker/src/log.ts`, mirrored for `apps/web`) that emits single-line JSON via `console.info`/`console.error` with a fixed field allowlist per event category (job transitions, Redis events, storage events, AI events) and a redaction check that throws in development if a disallowed key (`token`, `password`, `secret`, `signedUrl`, `credential`, …) is present in the payload.
- **Rationale**: "Basic operational visibility," not "a full monitoring platform," per the spec; a hand-rolled allowlisted JSON logger needs no new dependency (the only new dependency this feature requests is `ioredis`, already flagged) and is trivially greppable/ingestible by any log pipeline the deployment already uses (Docker's own log driver, per `docker-compose.yaml`).
- **Alternatives considered**: `pino`/`winston` — rejected as an unnecessary new dependency for a requirement this small; AGENTS.md requires justifying new packages, and a ~30-line allowlisted JSON emitter meets every FR-046–FR-050 requirement without one.

### 10. Observability surface

- **Decision**: Extend the existing `GET /api/health` (currently Postgres-only, via `getWebReadiness`) to also probe Redis and MinIO (mirroring the three-probe pattern `apps/worker/src/readiness.ts` already uses at startup, via the shared `probeProvider` helper from `@annotationplatform/domain`) and to include the counts FR-051 requires (queue backlog via BullMQ's own `getJobCounts`, active/failed/stale/retry/dead-letter counts via simple grouped Prisma counts on `Job`). No new "monitoring platform" route or dashboard — one extended JSON endpoint, consistent with "reuse existing health/readiness infrastructure."
- **Rationale**: `getWebReadiness`/`probeProvider` already exist and already express exactly the "is this dependency reachable" check this needs; extending them is strictly additive and keeps one canonical health surface instead of a second one.
- **Alternatives considered**: A dedicated `/api/metrics` (Prometheus-format) endpoint — rejected as beyond "basic operational visibility" for this phase; can be layered on top of the same counts later without redesign if ever needed.

### 11. Properties Panel pagination & label creation

- **Decision**: `AssetNavigator`/`ImagePropertiesTabs`/`VideoPropertiesTabs`/`PlaceholderPropertiesTabs` already accept `page`/`pageSize` as props and already render working Previous/Next controls (`asset-navigator.tsx`) — the only change is the `pageSize` value the workspace page computes and passes down (`apps/web/src/app/(app)/workspace/[datasetId]/page.tsx`), from its current default to `10`. For label creation, replace the Labels tab's name-only `<input>` + hardcoded `color: "#0EA5E9"` in `image-properties-tabs.tsx` with the same fields already built in `apps/web/src/components/labels/label-form.tsx` (name, visual color palette/picker, editable "Color code" hex field), calling the same `POST /api/datasets/[datasetId]/labels` endpoint the panel already calls. For "Add defaults," add explanatory copy (tooltip or inline caption) next to the existing button describing that it establishes *this dataset's own* default label set (via `ensureDefaultImageLabelsAction`, already wired) rather than relying on labels that merely look the same.
- **Rationale**: Zero new components needed — this is prop plumbing plus reusing an existing, already-styled form component, matching "preserve existing workspace behavior" and "reuse existing patterns."
- **Alternatives considered**: A new standalone color-picker for the panel — rejected as duplicating `label-form.tsx`.

### 12. Docker Compose verification

- **Decision**: No structural change expected — `docker-compose.yaml` already defines `postgres`, `redis`, `minio`, `web`, `worker` (plus `gitea`). Verification is a documented `docker compose up` run confirming all five reach a healthy/ready state and that a submitted job completes end-to-end (User Story 9's independent test), captured in `quickstart.md`. Any new environment variables this feature introduces (recovery/timeout thresholds, retention periods, rate-limit config) get added to the compose file's `worker`/`web` service `environment:` blocks with documented defaults.
- **Rationale**: Section 21 of the original request asks to "update Docker Compose documentation and configuration" and "verify" startup — the services already exist, so this is a documentation/verification task, not new infrastructure.
- **Alternatives considered**: None — building new compose services would contradict "do not create unnecessary additional services."
