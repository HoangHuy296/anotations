# Phase 0 Research: AI Integration through BullMQ

All Technical Context items had a resolvable answer from the existing codebase and architecture-lock docs; no `NEEDS CLARIFICATION` markers remain. Findings below are ordered by the decision's blast radius.

**Finalized terminology** (used consistently from here through `tasks.md`): `AiProviderSubmitInput` / `AiProviderSubmitResult` (submit call), `AiProviderStatusResult` (poll call — carries `status` plus, when `COMPLETED`, `predictions`), `AiProviderPrediction` (one normalized prediction inside `AiProviderStatusResult.predictions`). All four are defined once in `packages/domain/src/ai-provider.ts` (see decision #3).

## 1. How does a poll cycle get re-triggered without breaking the "one delivery per Job" transport rule?

**Decision**: Polling is driven by a PostgreSQL-backed interval **scanner** in the worker process (`apps/worker/src/queue/ai-poll-scanner.ts`), not by re-adding delayed BullMQ jobs. The scanner runs on a short `setInterval` (started in `readiness.ts` alongside the existing 60s `import-timeout-scanner.ts`), queries `AiTask` rows where `status IN (QUEUED, RUNNING)` and `nextPollAt <= now()`, and invokes `processAiPoll(db, jobId)` for each due row (bounded batch size, same shape as `failExpiredPreparedImports`). Each poll step recomputes `AiTask.nextPollAt` with backoff instead of scheduling a new queue delivery.

**Rationale**: `apps/web/src/lib/jobs/authorization.ts` → `enqueueExistingJob()` stamps `queueName`/`queueJobId` and guards on `job.enqueuedAt === null`, i.e. a durable `Job` is delivered through BullMQ **at most once** in this codebase's established contract. `docs/bullmq-postgres-job-flow.md` also fixes the queue payload to `{ jobId }` only and treats BullMQ purely as delivery-intent transport, not a scheduler for business-level retries. The schema already anticipates a scan-driven design: `AiTask.nextPollAt` exists with its own index (`@@index([nextPollAt])`), which is the natural key for a scanner query and has no equivalent purpose if polling were BullMQ-delay-driven. The codebase already has two precedents for exactly this shape of "recheck PostgreSQL on an interval" work: `import-timeout-scanner.ts` (`failExpiredPreparedImports`) and `recovery-scanner.ts` (`runPendingJobRecovery`), both invoked via `setInterval` in `readiness.ts`.

**Alternatives considered**:
- *BullMQ delayed self-re-add* (`queue.add("ai-poll", { jobId }, { delay })` from inside the poll processor, as sketched in the feature request's pseudocode): rejected. It would require either bypassing `enqueueExistingJob`'s one-shot guard (weakening a rule the rest of the platform depends on) or inventing a second, AI-specific queue-delivery path with its own dedupe/idempotency semantics — duplicating machinery `docs/job-system.md` already centralizes in `Job`. It also reintroduces Redis as a de facto scheduling store for business timing, which `bullmq-postgres-job-flow.md`'s "Operational limits" section explicitly warns against ("Do not use queue progress as a browser-visible source of truth" / PostgreSQL owns state).
- *BullMQ repeatable job per AiTask*: rejected for the same reason plus added operational complexity (one repeatable job definition per in-flight task, explicit cleanup on terminal state).

## 2. What lock primitive does a scanner-driven, multi-step poll loop need?

**Decision**: Add `apps/worker/src/queue/job-lock.ts` with `renewOrReclaimLock(db, jobId, workerId)` and `renewLock(db, jobId, lockToken, extendByMs)`, implemented as parameterized `UPDATE ... WHERE ... RETURNING` statements (same style as `job.repository.ts#claimJob`), operating only on `Job.lockedBy` / `lockToken` / `lockedUntil` / `heartbeatAt`. `renewOrReclaimLock` succeeds when either (a) the caller already holds the lock (`lockedBy = workerId` — issues a fresh `lockToken` and extends `lockedUntil`), or (b) no other worker's lease is currently valid (`lockedUntil IS NULL OR lockedUntil < NOW()`), in which case it takes over the lock. It requires `status = 'RUNNING'` and refuses (does not throw) when a *different* worker's lease is still valid — mirroring the existing `ClaimResult`/`LeaseMutationResult` "refused, don't throw" style in `job-claim-lock.ts`.

**Rationale**: The existing `claimJob` (`job.repository.ts`) only transitions `QUEUED|RETRYING → RUNNING` once; it is not re-enterable for a `Job` that is already `RUNNING` across many later scanner ticks. `heartbeatJob`/`updateJobProgress` in `job-claim-lock.ts` renew an *already-held, matching* `lockToken` but refuse outright if the lease expired or a different token is presented — correct for a single continuously-running worker process, but AI polling is intentionally re-entered by (possibly) different scanner ticks/worker instances over up to `MAX_POLL_DURATION_MS` (20 minutes), so a worker restart between ticks must be able to reclaim an expired lease rather than being permanently refused. This is the literal "renew-or-reclaim" requirement from the feature request, and it is additive: it does not change `job-claim-lock.ts`'s existing one-shot claim/heartbeat/complete/fail/cancel behavior, which other job types keep using unmodified.

**Alternatives considered**: Extending `heartbeatJob` to also reclaim expired leases — rejected to avoid changing behavior every other `JobType`'s worker path already relies on; a new, narrowly-scoped primitive is safer and matches the file the feature request already names (`apps/worker/src/queue/job-lock.ts`).

## 3. Provider resolution boundary — and which app owns it

**Decision (revised — see "Revision history" at the end of this section)**: The `AiProviderAdapter` contract is split across two locations by whether it touches Prisma/the network:

- **`packages/domain/src/ai-provider.ts`** (new, pure, no Prisma, no `fetch`): the `AiProviderAdapter` interface (`submitTask`, `getTaskStatus`) plus its supporting types — `AiProviderSubmitInput`, `AiProviderSubmitResult`, `AiProviderStatusResult`, `AiProviderPrediction`. This is the one piece both `apps/web` and `apps/worker` could import (both already depend on `@annotationplatform/domain`), kept here purely so the *shape* of the contract has one canonical definition, matching how `provider-config.ts`/`source-access-policy.ts` already work in this package (`zod`-typed, dependency-free).
- **`apps/worker/src/providers/ai/ai-provider-registry.ts`** (worker-only): `resolveAiProviderForTask(db, aiTask)` — loads `AiModel` by `aiTask.modelId` (a real Prisma call), throws a typed `AiTaskError("AI_MODEL_INACTIVE")` if `!model.isActive`, and looks up the concrete adapter keyed by `model.provider` (e.g. `"aioz-company"` — mirrors `AiModel.provider`'s existing Prisma comment "khớp AiProviderAdapter registry").
- **`apps/worker/src/providers/ai/aioz-company.provider.ts`** (worker-only): the concrete `AiProviderAdapter` implementation — the only code in the entire feature that makes an outbound HTTP call to the external AI service.

`apps/web` never imports any of the three files above. It only ever reads `AiModel.isActive`/`displayName`/`modality`/`taskType` as plain Postgres columns (`ai-model-service.ts`, `ai-task-service.ts`) — it has no reason to resolve or hold an adapter instance, since it never calls the provider itself (submission happens asynchronously in the worker, per decision #1, precisely so `POST /api/ai/tasks` can satisfy FR-006's "acknowledge without waiting on the provider"). `Job.provider` (`RepoProvider?`) is never read or written anywhere in `apps/web/src/lib/ai/**`, `packages/domain/src/ai-provider.ts`, or `apps/worker/src/providers/ai/**`/`apps/worker/src/jobs/ai-*.ts` — enforced structurally by never selecting that field in any Prisma query these modules issue.

**Rationale**: Matches the existing dual-registry precedent — `apps/web/src/lib/providers/provider-registry.ts` (`getRepositoryProvider`) already keys a `Record<Provider, Adapter>` off a string/enum and throws a typed error (`PreflightError`) for an unsupported value, exactly the shape `resolveAiProviderForTask` needs. Keeping `AiModel.provider` a plain string (already the schema's shape, not a Prisma enum shared with `RepoProvider`) is what structurally prevents the two "provider" concepts from being conflated — they are different Prisma types (`String` vs `RepoProvider` enum), so no code path can accidentally pass one where the other is expected without a type error. The `packages/domain`/`apps/worker` split additionally resolves a real defect in this decision's first draft (caught during `/speckit-tasks` and `/speckit-analyze`): `apps/worker` has no import path to `apps/web/src/lib` at all (verified: no `apps/web` import exists anywhere under `apps/worker/src`), so a registry/adapter placed only under `apps/web/src/lib/ai/` would have been unreachable dead code from the worker's perspective — the only process that actually calls the provider.

**Alternatives considered**:
- Reusing `RepoProvider` enum for `AiModel.provider` — rejected; the schema (already committed) deliberately keeps `AiModel.provider` a `String`, and widening the shared enum would be exactly the conflation `AGENTS.md`/the feature request forbid.
- Building the full contract + concrete adapter under `apps/web/src/lib/ai/` (the feature request's original literal paths) — rejected; see the dead-code problem above. `apps/web` calling the provider directly (even just `submitTask`, synchronously, on the request path) was also considered and rejected because it would make `POST /api/ai/tasks`'s response latency depend on the external provider's latency, contradicting FR-006.
- Putting the *entire* registry (including the Prisma `AiModel` lookup) in `packages/domain` — rejected; every other shared file in that package is deliberately Prisma-free (`package.json` lists only `zod` as a dependency), and introducing a generated-Prisma-client dependency there would break that convention for every future consumer of the package, not just this feature.

**Open dependency (blocks `aioz-company.provider.ts` implementation)**: The external AIOZ-company AI service's actual request/response contract (submit endpoint, auth header shape, submit request/response body, status-check request/response body, error shape) is not yet available to this repository. `apps/worker/src/providers/ai/aioz-company.provider.ts` must be written against the real contract, not a guessed one — implementing it from an assumption risks a rewrite of both the adapter and the poll-processor's result handling once the real shape is known. This file, and any task that depends on knowing the real `AiProviderStatusResult`/`AiProviderPrediction` shape, is blocked until the contract is supplied.

## 4. Transaction + post-commit enqueue shape for `POST /api/ai/tasks`

**Decision**: `createAiTask()` in `apps/web/src/lib/ai/ai-task-service.ts` follows the established three-step shape already used by `apps/web/src/lib/jobs/authorization.ts#createAndEnqueueFoundationJob` and `apps/web/src/lib/repository-import (createAndEnqueue*)`: (1) authorize + validate outside any transaction (`requireDatasetPermission(actor, datasetId, "annotation.create")`, `assertAssetsBelongToDataset`, active-`AiModel` check), (2) `db.$transaction(async (tx) => { create Job; create AiTask })`, (3) `enqueueExistingJob(job.id, ...)` strictly after the transaction resolves. Route responds `202 Accepted` with `{ taskId, jobId }`, matching the spec's "acknowledge immediately" requirement (FR-006) and this codebase's convention of using `enqueueExistingJob`'s own status-code mapping (`201`/`200`/`202` depending on whether Redis delivery itself is immediate or deferred-but-durable) rather than a hardcoded status.

**Rationale**: `AiTask.jobId @unique` makes the 1:1 invariant a database constraint, so no manual duplicate-check is needed inside the transaction (confirmed against the committed schema). Doing authorization/validation *before* opening the transaction avoids holding a transaction open for a request that is certain to be rejected — the same rationale already documented inline in `createAndEnqueueSourceImportJob`. Enqueue-after-commit is the platform-wide rule (`docs/bullmq-postgres-job-flow.md`: "Do not enqueue a Job before its durable record exists"), already applied consistently since Phase 6/015.

**Alternatives considered**: Enqueuing inside the transaction (rejected — violates the documented commit-before-enqueue rule and risks delivering a `jobId` that a rolled-back transaction never durably created). Returning `201` unconditionally (rejected — the feature request explicitly calls for `202` since AI processing is asynchronous, and `enqueueExistingJob`'s existing pending-delivery path already needs a non-`201` status for the "Job durable but Redis momentarily unavailable" case).

## 5. Wiring a new `JobType` pair into the single existing dispatcher

**Decision**: Add `"AI_PREANNOTATE_ASSET"` and `"AI_PREANNOTATE_DATASET"` to `supportedQueueJobTypes` in `packages/queue/src/job-contract.ts` (both already exist as `JobType` enum values in the committed schema), and add two dispatch lines to `apps/worker/src/queue/queue-router.ts#routeQueueDelivery` calling `processAiSubmit(db, job.id, claim.lockToken)` — following the exact `if (job.type === "...") await process...()` pattern already used for `IMPORT_DATASET`/`EXPORT_DATASET`/etc. No new queue, no new BullMQ `Worker` instance, no change to `fieldframeQueueName`.

**Rationale**: `queueNameForJobType` currently returns `null` for `AI_PREANNOTATE_*` (not yet in the allowlist), which means `authorizeFoundationJobSubmission`/`enqueueExistingJob` would reject an AI task today — this addition is required, not optional, and is the minimal change consistent with "one shared queue, one router" already established.

**Alternatives considered**: A second BullMQ queue dedicated to AI jobs — rejected; `docs/architecture.md`'s Phase 0 lock and every later phase use exactly one queue name (`fieldframe-jobs`) with `{ jobId }` payloads; introducing a second queue is unjustified complexity for a feature that still routes through the same durable `Job`/claim/lock lifecycle.

## 6. Persisting predictions as `Annotation` rows

**Decision**: `apps/worker/src/jobs/ai-prediction-writer.ts#handleAiTaskCompleted()` receives the worker's normalized `AiProviderPrediction[]` (already converted from the AIOZ-company API's raw response by `aioz-company.provider.ts`/`getTaskStatus()` — the adapter itself never touches Prisma; see decision #3), validates that array's *application-level* shape with Zod (`assetId`, `labelKey`, `confidence`, `boundingBoxes`), discards any prediction whose `assetId` is not in `aiTask.input.assetIds` (FR-015), resolves each `labelKey` against `Dataset.labels` (skipping — not failing the whole task — a prediction that names an unresolvable label, per the spec's Edge Cases), and `tx.annotation.create()`s one row per valid prediction with `source: "AI"`, `status: "DRAFT"`, `createdById: aiTask.createdById`, `modality: aiTask.modality`, `type` derived from `AiModel.taskType` (e.g. `DETECT_OBJECTS → BOUNDING_BOX`), and `properties: { confidence, aiTaskId, modelKey: aiTask.modelKeySnapshot }`. `reviewedById` is left `null`. The same transaction sets `AiTask.status = "SUCCEEDED"`, `AiTask.output`, and `Job.status = "COMPLETED"` / `stage = "FINISHED"` / `finishedAt`. The code path only ever calls `tx.annotation.create()` — never `update()`/`delete()` against an existing `Annotation` row — which is what structurally guarantees `source = MANUAL` rows are untouched (FR-016), independent of any runtime filter. This split (adapter emits `AiProviderPrediction[]`; a separate worker module validates/writes) keeps the provider layer free of any Prisma import, matching the explicit constraint that a provider implementation must never call `prisma.annotation.create(...)` or any other Annotation mutation.

**Rationale**: Every field used already exists on `Annotation` (`source`, `status`, `properties`, `reviewedById`) exactly as the schema defines them — no migration needed. `Annotation.type` needs a concrete mapping since `AiModel.taskType` (`AiTaskType` enum: `DETECT_OBJECTS`, `SEGMENT_IMAGE`, `TRANSCRIBE_AUDIO`, `CLASSIFY_TEXT`, `CLASSIFY_AUDIO`, `PREANNOTATE_ASSET`, `PREANNOTATE_DATASET`, `CUSTOM`) and `Annotation.type` (`AnnotationType` enum) are different enums; this phase implements the `DETECT_OBJECTS → BOUNDING_BOX` mapping needed for the image bounding-box path the spec's User Story 1 describes as the primary flow, and treats any other `AiTaskType` as out of scope until a future phase's model/task pairing is defined (documented as a known limitation, not a blocker).

**Alternatives considered**: Failing the entire `AiTask` if any single prediction is malformed/unresolvable — rejected; spec's Edge Cases and Assumptions explicitly call for skipping the individual prediction instead.

## 7. Cancellation surface

**Decision**: No new AI-specific cancel endpoint. `Job.cancelRequestedAt` is the single cancellation signal, already settable through the existing `POST /api/jobs/[jobId]/cancel` → `cancelAuthorizedJob()`. The poll processor's cancellation check (`job.cancelRequestedAt`, read after acquiring the lock, before calling the provider) is the only new cancellation-aware logic this feature adds.

**Rationale**: `AiTask.jobId` 1:1 means "cancel the Job" already *is* "cancel the AiTask" at the architecture level; building a parallel `/api/ai/tasks/[aiTaskId]/cancel` would duplicate `cancelAuthorizedJob`'s existing QUEUED/RETRYING/RUNNING state-machine handling for no behavioral gain, and AGENTS.md's Job/AiTask boundary treats `Job` as owning "internal processing lifecycle" including cancellation.

**Alternatives considered**: A dedicated `/api/ai/tasks/[aiTaskId]/cancel` that internally forwards to the Job cancel path — rejected as pure duplication; frontend/API consumers needing to cancel an AI task can resolve `AiTask.jobId` (already returned by `GET /api/ai/tasks/[aiTaskId]`) and call the existing endpoint.
